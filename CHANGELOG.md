## feature-5 — команда /edit_event — 2026-08-04

Реализовано редактирование события: выбор списка (🗓 прошедшие / 📅
предстоящие, как в `/delete_event`) → выбор события → по очереди
4 вопроса «изменить это поле?» (название/дата/время/описание —
четвёртое поле сверх исходных 3 из брифа, добавлено для консистентности
с `/add_event`) → если хоть что-то поменяли — экран подтверждения
только с изменёнными полями («старое → новое») → сохранение. Если на
все 4 вопроса ответили «нет» — выход без подтверждения, без лишнего
клика. Нет событий вообще → шуточная фраза + кнопки «➕ Создать
событие» (запускает `/add_event`) / «❌ Отмена».

В БД: `update_event` — частичное обновление, меняет только реально
изменённые колонки (не перезаписывает всю строку).

Заодно: `_build_scope_keyboard`/`_build_event_choice_keyboard` (шаги
"список"/"выбор события") обобщены и теперь общие для `/delete_event`
и `/edit_event` вместо двух похожих копий; `/edit_event` добавлена в
меню команд Telegram.

## feature-4 — команда /delete_event — 2026-08-04

Реализовано удаление события: выбор списка (🗓 прошедшие / 📅
предстоящие — шаг показывается, только если оба списка непустые, иначе
сразу открывается тот, что есть) → список кнопками → экран
подтверждения с обязательными деталями (название+дата+время,
единственная защита от удаления не того события, действие необратимо)
→ «Удалить»/«Отменить». Отдельного сообщения об успехе нет (по брифу —
достаточно обновлённого закрепа; закреп ещё не реализован, TODO).

Списки разделены на предстоящие/прошедшие (а не один общий список из
всех событий чата) — иначе в чате, который живёт больше года, список
превращался бы в нечитаемую портянку из давно неактуальных записей.

Без FSM/состояний — id события (и выбранный список) едут прямо в
callback_data кнопок между шагами. В БД добавлены `get_past_events`,
`get_event_by_id` (с проверкой chat_id — событие одного чата нельзя
достать/удалить из другого, даже подставив чужой id) и `delete_event`.

Заодно: команды теперь регистрируются в меню Telegram (кнопка "/") при
каждом старте бота через `bot.set_my_commands` — раньше список команд
там был пустым, приходилось набирать вручную и помнить наизусть.

## feature-3 — команда /next_event — 2026-08-04

Реализован показ самого ближайшего предстоящего события: `/next_event`
берёт первую запись из уже существующей `get_upcoming_events`
(отсортирована от ближайшего к дальнему — специальный SQL-запрос не
понадобился). Формат: дата (+время) — название, описание отдельной
строкой при наличии, и всегда — «через сколько дней» (сегодня/завтра/
через N дней). Событие сегодняшнего дня остаётся «ближайшим» весь день,
даже если время начала уже прошло. Нет событий → случайная фраза
MSG_NO_EVENTS.

Построение строки «дата (+время) — название» вынесено в общий хелпер
`_format_event_title_line`, переиспользуется и в `/all_events`.

## feature-2 — команда /all_events — 2026-08-04

Реализован просмотр всех предстоящих событий чата: `/all_events` выводит
полный список без ограничения на 30 дней вперёд (в отличие от будущего
закрепа), от ближайшего события к дальнему. Прошедшие события в список
не попадают. Если событий нет — случайная фраза из MSG_NO_EVENTS.
Самое ближайшее событие в списке, если оно ближе чем через 2 недели,
получает пометку «‼️через N» (N — сегодня/завтра/через столько-то дней,
с правильным русским склонением). Если у события есть описание —
показывается отдельной строкой под датой и названием.

Заодно в БД добавлена переиспользуемая функция выборки предстоящих
событий (`get_upcoming_events`) — пригодится и для будущего `/next_event`.

## bugfix-1 — 2026-08-04

**Исправлено:** `/add_event` зависал на кнопке «Подтвердить» и не
сохранял событие — падал с ошибкой SQLite
`table events has no column named description`.

**Причина:** файл БД (`data/coworking.db`) был создан ещё до того, как
в схему добавили поле `description`. `CREATE TABLE IF NOT EXISTS` не
трогает уже существующие таблицы — новая колонка в реальном файле
физически не появилась.

**Фикс:** при каждом старте бота теперь проверяется список обязательных
колонок и через `ALTER TABLE` дописываются недостающие, без потери
уже сохранённых данных.

PR: #2 (`bugfix-1` → `main`)

## feature-1 — команда /add_event — 2026-08-04

Реализован полный сценарий добавления события: `/add_event` запускает
пошаговый диалог — название → дата (ДД.ММ.ГГГГ) → время (необязательно,
кнопки «Добавить время» / «Пропустить») → описание (необязательно,
кнопки «Добавить описание» / «Пропустить») → экран подтверждения →
сохранение в БД. `/cancel` прерывает диалог на любом шаге.

Заодно: все тексты бота вынесены в отдельный модуль `bot/messages.py`,
бриф синхронизирован с реализацией (поле `description` в EVENTS,
обновлён сценарий, добавлены тексты шагов).

PR: #1 (`feature/add-event-command` → `main`) — ветка названа ещё до
того, как договорились об именовании `feature-N`/`bugfix-N`.
