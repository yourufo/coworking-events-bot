# Передача проекта — чек-лист

Этот файл — для передачи проекта коллегам, которые продолжат разработку.
Публичный GitHub-репозиторий даёт им **код, историю и документацию**
(`PROJECT_BRIEF.md`, `CHANGELOG.md`, `README.md`), но не даёт работающего
бота — вот что нужно передать/решить дополнительно.

---

## 1. Права на запись в репозиторий

Публичный репозиторий = все могут **читать** и клонировать, но
**пушить/мёржить** могут только коллабораторы.

- [ ] Добавить коллег в **Settings → Collaborators → Add people**
      (нужны их GitHub-юзернеймы)

Без этого коллеги смогут работать только через форк + Pull Request со
стороны — тоже вариант, но лишний шаг.

---

## 2. Токен бота (`BOT_TOKEN`) — специально НЕ в git

`.env` и `data/*.db` в `.gitignore` намеренно (см. `bot/config.py`).
Клонировав репозиторий, коллеги получат код, но не смогут запустить
именно этого бота (`@Coworking_event_bot`) без токена.

- [ ] Решить: передавать реальный токен или заводить тестовые боты (см. ниже)
- [ ] Если передавать — только через менеджер паролей / секретный чат
      в Telegram, никогда открытым текстом в Slack/почте

**Рекомендация:** каждому разработчику — свой тестовый бот через
@BotFather (`/newbot`, 2 минуты), а этот токен оставить только для
«боевого» инстанса. Причина — следующий пункт.

---

## 3. Один токен = один активный polling-процесс

Telegram не даёт двум процессам одновременно опрашивать (`getUpdates`)
один и тот же токен — если два человека одновременно запустят
`python -m bot.main` с одним `BOT_TOKEN`, второй начнёт получать ошибки
конфликта. Ещё один аргумент за отдельные тестовые боты на разработку.

---

## 4. Хостинг — этого пока нет вообще

Бот пока нигде не развёрнут постоянно — запускается только вручную
(`python -m bot.main`) на том компьютере/сессии, где его кто-то включил.
Как только процесс остановится — бот перестаёт отвечать.

- [ ] Выбрать, где бот будет работать постоянно: сервер/VPS,
      Docker-контейнер, systemd-сервис или облачная платформа
      (Railway/Render/etc.)
- [ ] Это решение ещё не задокументировано в `PROJECT_BRIEF.md` —
      стоит добавить туда раздел, когда решение будет принято

---

## 5. Файл БД с текущими тестовыми данными

`data/coworking.db` — тоже не в git. Внутри только тестовые записи,
добавленные по ходу проверки функциональности.

- [ ] Решить: передать файл коллегам (если хотят продолжить с теми же
      тестовыми данными) или начать с чистой БД — `init_db()` создаст
      её заново автоматически при первом запуске, ничего готовить
      вручную не нужно

---

## 6. Что уже готово и передавать отдельно не нужно

- `PROJECT_BRIEF.md` — архитектура, все сценарии, ключевые решения
  (включая нюансы, доработанные в процессе)
- `CHANGELOG.md` — история фич и багфиксов, новые записи сверху
- `README.md` — структура проекта, доступные команды, инструкция запуска
- Раздел 6 `PROJECT_BRIEF.md` — соглашения о разработке (нейминг веток
  `bugfix-N`/`feature-N`, один PR на ветку, обновление CHANGELOG)

Переписка с Claude, в которой обсуждались и дорабатывались решения,
коллегам не передаётся и не нужна — все существенные решения уже
зафиксированы в перечисленных файлах.
