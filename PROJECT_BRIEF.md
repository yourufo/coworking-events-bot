# Coworking Events Bot — бриф проекта

Telegram-бот для группового чата коворкинга, который держит в голове события и дни рождения участников и даёт актуальную информацию по команде.

**Стек:** Python. Библиотека для Telegram — на твоё усмотрение (рекомендуется `python-telegram-bot` или `aiogram`, обе хорошо поддерживаются).

**Роль человека:** бизнес-системный аналитик, не разработчик. Пиши код с подробными комментариями, объясняй архитектурные решения по ходу работы — человек должен понимать, что происходит, даже не читая код профессионально.

---

## 1. Архитектура

Бот состоит из 4 блоков:

| Блок | Роль |
|---|---|
| **Telegram** | Источник сообщений от пользователей и канал отправки ответов |
| **Обработчик команд** | Основная логика: принимает сообщения, решает что делать |
| **Хранилище данных (БД)** | «Память» бота — хранит события и дни рождения |
| **Планировщик (Scheduler)** | Работает независимо от пользователей: раз в день проверяет, нужно ли отправить напоминание или обновить закреп |

Связи: Telegram ↔ Обработчик команд (двусторонняя) · Обработчик команд → БД (чтение/запись) · Планировщик → БД (самостоятельная проверка по расписанию) · Планировщик → Telegram (отправка напоминаний и обновление закрепа без участия пользователя).

**Главное отличие Планировщика от Обработчика команд:** работает сам по себе, без запроса от пользователя.

### Требование к настройке бота (обязательно для работы автообновления закрепа)
При добавлении бота в чат:
1. Назначить бота **администратором** чата
2. Выдать право **can_pin_messages**

Без этого `pinChatMessage` / `unpinChatMessage` будут возвращать ошибку.

## 2. Схема БД

### CHATS
| Поле | Тип | Описание |
|---|---|---|
| chat_id | bigint, PK | ID чата из Telegram |
| chat_title | string | Название чата |
| pinned_message_id | bigint | ID закреплённого сообщения |
| pinned_message_created_at | datetime | Время первой отправки текущего закрепа (нужно для проверки 48-часового окна) |

### USERS
| Поле | Тип | Описание |
|---|---|---|
| user_id | bigint, PK | ID пользователя из Telegram |
| username | string | @username (может отсутствовать) |
| first_name | string | Имя для отображения |

### EVENTS
| Поле | Тип | Описание |
|---|---|---|
| id | int, PK | Внутренний ID |
| chat_id | FK → CHATS | В каком чате |
| created_by | FK → USERS | Кто создал |
| title | string | Название события |
| event_date | date | Дата (ДД.ММ.ГГГГ) |
| start_time | time, nullable | Время начала (ЧЧ:ММ) — необязательное, можно пропустить |
| description | string, nullable | Описание события — необязательное, можно пропустить |

### BIRTHDAYS
| Поле | Тип | Описание |
|---|---|---|
| id | int, PK | Внутренний ID |
| chat_id | FK → CHATS | В каком чате |
| added_by | FK → USERS | Кто добавил |
| person_user_id | FK → USERS, nullable | Ссылка на участника чата, если выбран из списка |
| person_name | string | Имя для отображения (из профиля или введено вручную) |
| birth_day | int | День (1–31) |
| birth_month | int | Месяц (1–12) |
| birth_year | int, nullable | Год — может отсутствовать |

### REMINDER_LOG
| Поле | Тип | Описание |
|---|---|---|
| id | int, PK | Внутренний ID |
| source_type | string | "event" или "birthday" |
| source_id | int, FK | ID события/ДР |
| interval_type | string | "2_weeks" / "1_week" / "3_days" / "1_day" |
| sent_at | datetime | Когда фактически отправлено |

**Связи:** CHATS→EVENTS, CHATS→BIRTHDAYS (один-ко-многим) · USERS→EVENTS, USERS→BIRTHDAYS (кто создал) · EVENTS→REMINDER_LOG, BIRTHDAYS→REMINDER_LOG (история отправок).

### Почему так спроектировано
- **EVENTS и BIRTHDAYS — разные таблицы**: дата рождения повторяется каждый год, событие разовое. Разделение упрощает логику напоминаний.
- **birth_day/birth_month/birth_year раздельно, год nullable**: год рождения часто неизвестен для «внешних» именинников; раздельные поля упрощают поиск «ближайших ДР» без учёта года.
- **person_user_id + person_name**: именинник может быть участником чата (есть user_id) или «внешним» человеком (только текстовое имя).
- **REMINDER_LOG**: защита от повторной отправки одного и того же напоминания при перезапуске/сбое планировщика.

## 3. Сценарии (User Flow)

### Общий принцип
Все сценарии с вводом нескольких полей идут через **пошаговый диалог**: бот спрашивает поля по одному, валидирует каждый ответ сразу, в конце — экран подтверждения с кнопками «Подтвердить»/«Отменить». На любом шаге пошагового диалога работает команда **/cancel** — прерывает диалог немедленно, ничего не сохраняя.

---

### 1. Добавить событие — `/add_event`
1. Бот: «Введите название события» → текст
2. Бот: «Введите дату (ДД.ММ.ГГГГ)» → валидация формата, при ошибке — повтор только этого шага (MSG_INVALID_DATE)
3. Бот: «Указать время начала?» — кнопки «Добавить время» / «Пропустить».
   Добавить время → «Введите время (ЧЧ:ММ)» → валидация (MSG_INVALID_TIME).
   Пропустить → время не указано (NULL).
4. Бот: «Добавить описание?» — кнопки «Добавить описание» / «Пропустить».
   Добавить описание → «Введите описание события» → текст, без валидации формата (любой текст).
   Пропустить → описание не указано (NULL).
5. Экран подтверждения (MSG_EVENT_ADDED): название + дата + время + описание, кнопки Подтвердить/Отменить
6. Подтвердил → сохранить в EVENTS, закреп обновится автоматически (MSG_EVENT_SAVED). Отменил → ничего не сохранять.

### 2. Изменить событие — `/edit_event`
Объединяет редактирование всех 3 полей в одном диалоге.
1. Ищем события в чате. Нет → шуточная фраза MSG_NO_EVENTS_TO_EDIT + кнопки «Отмена»/«Создать событие» (ведёт в /add_event). Есть → список кнопками.
2. Выбор события из списка.
3. «Изменить название?» да/нет → да: новое название текстом; нет: пропуск.
4. «Изменить дату?» да/нет → аналогично, валидация формата.
5. «Изменить время?» да/нет → аналогично.
6. Если все три «нет» → выход без подтверждения.
7. Иначе — экран подтверждения только с изменёнными полями («старое → новое»).
8. Подтвердил → сохранить (MSG_EVENT_UPDATED), закреп обновится. Отменил → не сохранять.

### 3. Удалить событие — `/delete_event`
1. Ищем события, отдельно предстоящие и прошедшие (не один общий список — см. «Ключевые решения»).
   - Обоих списков нет → шуточная фраза MSG_NO_EVENTS_TO_DELETE.
   - Есть только один из двух списков → сразу показываем его (список кнопками), шаг выбора списка пропускаем.
   - Есть оба → «Из какого списка удалить?» — кнопки 📅 Предстоящие / 🗓 Прошедшие, затем список кнопками выбранной категории.
2. Выбор события из списка.
3. «Удалить это событие?» — **обязательно показать детали (название+дата+время)**, не только название — единственная защита от случайного удаления не того события (действие необратимо). Кнопки Удалить/Отменить.
4. Удалил → удалить из EVENTS, закреп обновится автоматически. **Отдельное сообщение в чат НЕ отправляется** (MSG_EVENT_DELETED) — закрепа достаточно. Отменил → без изменений.

### 4. Показать ближайшее событие — `/next_event`
Чистое чтение, без диалога.
1. Ищем событие с минимальной датой ≥ сегодня.
2. Найдено → название, дата, время, «через сколько дней».
3. Не найдено → случайная фраза из MSG_NO_EVENTS (см. список ниже).

**Важный нюанс:** события сегодняшнего дня всегда актуальны, даже если время начала уже прошло (в БД нет времени окончания события — нет надёжного способа понять, что оно завершилось).

### 5. Показать все запланированные события — `/all_events`
Дополняет закреп (тот ограничен 30 днями) — выводит весь горизонт без ограничения по дате.
1. Все события чата, сортировка от ближайшего к дальнему.
2. Есть → полный список (формат MSG_ALL_EVENTS). Нет → случайная фраза MSG_NO_EVENTS.

### 6. Добавить день рождения — `/add_birthday`
1. «Кто именинник?» — список участников чата кнопками + кнопка «Другое имя».
2. Выбор из списка → имя+user_id фиксируются автоматически. ИЛИ «Другое имя» → ввод текстом (для людей вне чата).
3. Проверка: есть ли уже запись ДР для этого человека (по person_user_id или person_name).
   - Есть → MSG_BIRTHDAY_EXISTS, предложение перейти к /edit_birthday, сценарий завершается.
   - Нет → дальше.
4. «Введите день и месяц (ДД.ММ)» → валидация (MSG_INVALID_DAY_MONTH).
5. «Указать год рождения?» Указать/Пропустить → указать: запросить год (валидация MSG_INVALID_YEAR); пропустить: birth_year = NULL.
6. Экран подтверждения: имя + дата (с годом или без).
7. Подтвердил → сохранить в BIRTHDAYS (MSG_BIRTHDAY_SAVED). Отменил → не сохранять.

**Важно:** один человек = одна запись. Повторное добавление не создаёт дубль, предлагает редактирование.

### 7. Изменить день рождения — `/edit_birthday`
Можно менять любое из 3 полей: имя/привязку, день+месяц, год. Позволяет перепривязать именинника с «внешнего» на участника чата (и наоборот).
1. Ищем записи ДР. Нет → сообщение, сценарий завершается (MSG_NO_BIRTHDAYS_TO_EDIT). Есть → список кнопками.
2. Выбор записи.
3. «Изменить имя/привязку?» да/нет → да: тот же выбор, что в добавлении (список участников + «Другое имя»).
4. «Изменить день и месяц?» да/нет → валидация формата.
5. «Изменить год рождения?» — **три кнопки**: Изменить / Убрать год / Оставить как есть.
   - Изменить → запросить новый год.
   - Убрать год → birth_year = NULL.
   - Оставить → без изменений.
6. Если ничего не изменилось → выход без подтверждения.
7. Иначе — экран подтверждения только с изменёнными полями.
8. Подтвердил → сохранить (MSG_BIRTHDAY_UPDATED). Отменил → не сохранять.

### 8. Показать список дней рождения — `/birthdays`
Чистое чтение, без диалога, **прямо в групповом чате** (без приватности — см. решение ниже).
1. Все записи ДР чата, сортировка по дню+месяцу (год игнорируется при сортировке).
2. Есть → список: имя, дата, возраст (если год известен). Нет → MSG_NO_BIRTHDAYS («Дней рождения пока нет»).

### 9. Напоминания по расписанию (автоматика, без участия пользователя)
1. Планировщик запускается 1 раз в день (утром).
2. Собирает все события и ДР во всех чатах.
3. Для каждого события — 4 интервала: 2 недели / 1 неделя / 3 дня / 1 день. Для каждого ДР — только 1 интервал: 2 недели (чтобы не портить сюрприз и не быть избыточным).
4. Для каждого интервала: сегодня + интервал == дата события/ДР? Сравниваются только даты, время не участвует.
5. Совпало → проверка REMINDER_LOG (уже отправляли?).
6. Не отправляли → отправить по шаблону MSG_REMINDER + записать в REMINDER_LOG. Отправляли → пропустить.

### 10. Автообновление закрепа (автоматика, два независимых механизма)
Закреп показывает только события/ДР в пределах ближайших **30 дней**. Полный список — отдельная команда /all_events (см. п.5).

**Механизм 1 — реактивный (в реальном времени).** Срабатывает сразу после действия пользователя при любом из условий:
- Создали/изменили/удалили событие в пределах 30 дней
- Дата события, ранее за пределами 30 дней, попала в этот диапазон (выявляется при ежедневной проверке планировщика)
- Создали/изменили/удалили ДР в пределах 30 дней

Действие: `editMessageText` — просто редактирует текст текущего закрепа.

**Механизм 2 — плановый (проверка раз в день, но действует только при необходимости).** В той же ежедневной проверке, что и напоминания:
1. Проверить: сколько времени прошло с момента первой отправки текущего закрепа (поле `pinned_message_created_at` в CHATS).
2. Меньше 47 часов → ничего не делать.
3. ≥ 47 часов → пересоздать: `sendMessage` (новое сообщение по шаблону MSG_PIN) → `pinChatMessage` → `unpinChatMessage` + `deleteMessage` (старое) → обновить `pinned_message_id` и `pinned_message_created_at` в CHATS.

**КРИТИЧЕСКИ ВАЖНО:** Telegram позволяет редактировать сообщение только **48 часов с момента его первой отправки**. Это окно фиксированное и НЕ продлевается повторными редактированиями. Поэтому нужны оба механизма: реактивный держит контент актуальным, плановый предотвращает упор в лимит редактирования. Пересоздание запускается ТОЛЬКО когда реально близко к истечению — не пересоздавать бессмысленно каждый день.

Используй единый модуль/файл с константами (например `messages.py`), а не разбросанные строки по коду — облегчает правки тона.

## 5. Ключевые решения и почему

| Решение | Почему |
|---|---|
| EVENTS и BIRTHDAYS — разные таблицы | ДР повторяется каждый год, событие разовое |
| Экран подтверждения перед сохранением | Шанс заметить опечатку, не плодить мусорные записи |
| /cancel на любом шаге диалога | Без этого пользователь вынужден домучивать диалог или вводить мусор |
| birth_day/month/year раздельно, год nullable | Год часто неизвестен для внешних именинников; упрощает поиск ближайших ДР |
| Время и описание события — необязательные, выбор кнопками «Добавить …» / «Пропустить» | Не все детали события известны в момент создания; не блокировать сохранение из-за необязательных полей — тот же паттерн, что и с годом рождения в ДР |
| Именинник: участник чата ИЛИ текст | Реальный кейс — помнить о ДР людей вне чата |
| Список ДР — прямо в группу, без приватности (пока) | Telegram не даёт боту писать в личку первым, пока юзер сам не нажал Start, а все наши сценарии групповые — повода для Start может не быть. Вернуться к этому позже можно через кнопку-ссылку "Написать боту" |
| Закреп пересоздаётся только при приближении к 48ч, не каждый день | 48-часовое окно редактирования Telegram фиксировано и не продлевается правками; ежедневное безусловное пересоздание избыточно |
| Бот должен быть админом с can_pin_messages | Иначе pinChatMessage/unpinChatMessage вернут ошибку |
| Закреп ограничен 30 днями, полный список — отдельной командой /all_events | Длинный список на весь год сделал бы закреп нечитаемым |
| При старте бота — авто-миграция колонок (ALTER TABLE, если колонки не хватает) | Схема БД со временем меняется (пример: поле `description` добавили после того, как у кого-то уже была рабочая БД); без миграции `CREATE TABLE IF NOT EXISTS` не трогает уже существующие таблицы — новая колонка просто не появится, и сохранение упадёт с ошибкой SQLite. Баг именно так и проявился, см. bugfix-1 в `CHANGELOG.md` |
| Списки событий "на выбор" (удаление, позже — редактирование) разделены на предстоящие/прошедшие, а не один общий список | Чат живёт больше года — единый список из всех событий подряд быстро превращается в нечитаемую портянку из давно неактуальных записей. Шаг выбора списка показывается, только если оба списка непустые — иначе это лишний клик без выбора |
| Команды регистрируются в меню Telegram (кнопка "/") при каждом старте бота (`bot.set_my_commands`), не разово вручную через BotFather | Список автоматически остаётся актуальным по мере появления новых команд — не нужно отдельно не забыть обновить его вручную при следующем релизе. `/cancel` в меню намеренно не включена — служебная команда, работает только посреди уже начатого диалога |

## 6. Соглашения о разработке

Не про архитектуру бота, а про то, как ведём сам проект — чтобы было
легко ориентироваться в ветках и истории изменений.

- **Именование веток:** `bugfix-N` — для исправлений (баги, опечатки,
  падения), `feature-N` — для новых команд/сценариев. N — следующий
  свободный порядковый номер для этого префикса.
- **Один PR на ветку.** Ветка → Pull Request в `main` → после мержа
  ветка удаляется. Так `main` всегда остаётся рабочим, а изменения
  видны и обсуждаемы по отдельности.
- **Коммит-сообщения и описания PR — ёмкие**: что изменилось и почему,
  без длинного пересказа кода.
- **История изменений — `CHANGELOG.md`** в корне репозитория: короткая
  запись на каждый мёрж (фича или багфикс), новые записи сверху, старые
  остаются снизу. Это дополняет git-историю человекочитаемым журналом —
  не нужно лезть в `git log`, чтобы понять, что и когда поменялось.
